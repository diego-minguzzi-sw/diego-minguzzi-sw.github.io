. Asynch Rust

Performance: futures make progress only when polled, async is zero cost.
Runtime : Rust has no built-in runtime. They are provided by third parties, like Tokio.
Async vs Threads: use async when there are many tasks. Async tasks are light. Threads require CPU and memory overhead. Spawning and switching between threads is quite expensive as even idle threads consume system resources.
A thread pool library can help mitigate some of these costs, but not all.

  • async / wait are implemented at language level
  • The Future struct and the futures crate are part of the standard library

To create an asynchronous function, you can use the async fn syntax:

async fn do_something() {}
async fn hello_world() {}

let future = hello_world();

futures::executor::block_on(future);

// Otherwise, the future can be passed to a Thread pool or some other executor.
The value returned by an code>async fn is a Future. For anything to happen, the Future needs to be run on an executor.

. Data types

.. Arrays

Arrays contain elements of the same type.
Arrays are allocated on the stack.
Array items are referenced with an index that starts from zero (48).
Items are stored in a contiguous section of memory.
Arrays have fixed length, there is no dynamic resize. The Array size must be known at compile time.
An array is like a row of parked cars. All parking lots contain the same thing, the number of lots is fixed.
An array is a data type parameterized by its items type and the number of items.
let words = ["English", "This", "sentence", "a", "in", "is"];

let other_array: [i32; 4]= [1,2,3,4];
// The size of the array and the number of items must match. 
let mut numbers: [i32; 4];
Here, the content is not specified. Useless if not mutable.
let b= [ 1u8; 10];
Createss an array of 10 items, all initialized to 1u8.
Note: 
  let another_array: [i32; 6] = [1,2,3,4,5,6]; // Explicit declaration of the array data type.
  let mut numbers: [i32; 5] = [0; 5]; // This notation creates an array of 5 items, initialized to zero.
  let more_numbers = [1i8; 5];        // Other example, the constant is 1, the data type is i8.
  let five_items= [1u32; 5];          // Five items, the init value is 1u32.  *** Useful ***

The String contains a pointer to the memory on the heap, its length and its capacity.
The String can be mutable. It has a pointer to the string memory, a length and a capacity.

.. Slices

Slice: a contiguous section of a collection.
The slice references the collection without taking ownership of it.

The generic form of a slice is &[T]
&str is a string slice. Note that string literals are slices too. How to declare a string slice. Examples:

  • let first_word= &message[..9];
  • let last_part= &message[15..];
  • let last_word= &message[15..20];
The compiler cannot know the collection boundaries.
So a slice that accesses out of the collection boundaries causes a panic and a program crash.
The length of a string slice is expressed into bytes, not characters.
Range indices must occur at valid UTF-8 character boundaries, otherwise the program will panic.

&String is different from &str
However, Rust allows us to use a String reference (&str) in places where a String slice is needed, since the String has all the data to function as a slice: pointer and length (the string has also the capacity).
It is not possible to convert a string slice into a reference to a String.
So, defining a function parameters as a string slice instead of reference to String , makes the signature more general and reusable.

Arrays, vectors, strings can be passed to functions as slices.
It is possible to take slices of slices.

  fn min( arr: &[i32] ) -> i32 { ... } // A function that has a slice argument.

  min(&arr);        // The function is called with the following syntax.
  min(&arr[2..5])   // The function is called with the slicing syntax.
  min(&arr[4..3])   // Backward slices cause runtime panic.

  min(&arr[2..])   // Slice from item 2 to the end.
  min(&arr[..3])   // Slice from the beginning to item 3, not included.

  2..=4 // The upper limit is included, this is called right inclusive range.

... Shadowing

Shadowing: declaring a new variable with the same name as an existing variable.

The new variable shadows the previous variable. This is different than creating a mutable variable.

Shadowing lets us reuse the guess variable name rather than forcing us to create two unique variables. 

This feature is often used when you want to convert a value from one type to another type.



Shadowing is different from marking a variable as mut because we’ll get a compile-time error if we accidentally try to reassign to this variable without using the let keyword. 

By using let, we can perform a few transformations on a value but have the variable be immutable after those transformations have been completed.



Shadowing allows to change the type and mutability of a variable (30).
That is, the shadowing variable can also have a different data type or mutability.

Not a different name, otherwise it would not be shadowing.

When the shadowing variable goes out of scope, the original variable still exists, with its original value.


Shadowing is useful to reuse certain common variable names.

    .. Borrowing and Ownership
    

Ownership requires to know how the stack and the heap are used to manage program data.
    

Scope : the specific region of a program where a variable is valid.

    
In Rust, variable bindings live within a block of code,
from the point where the variable is initialized until the end of the block.
    
Note that in Rust an error is raised if a variable is used before it is initialized.
    

Blocks of code are enclosed by curly braces.
    
Blocks of code evaluate to the last expression in them.
    

    

The rules of ownership:

      
  
    • each value has an owner (the owning variable)
      • 
  
    • there can be only one owner at an given time
      • 
  
    • when the owner goes out of scope, the value is dropped and the memory is deallocated.
      
      The memory is deallocated immediately after the data goes out of scope.
      • 

    
Rust never automatically creates deep copies of data.
    

Ownership
Ownership applies to references to objects in the heap.

    
Ownership rules:

      
  
    • Variables are responsible for freeing their own resources.
      • 
  
    • Every value is associated to one, and only one variable at a time
      • 
  
    • When the owning variable goes out of scope, the value is dropped.
      • 

    
Advantage of ownership: it is safe and efficient, deallocation can be determined at compile time.
    
Disadvantage: it requires understanding of ownership and to think differently.
    

Transferring the ownership of a variable to another is called move.
    
When we copy a String to another, we actually do a move operation.
    
In order to copy a value and not transfer ownership, the .clone() method is used.
    

    

    Rust will never automatically create “deep” copies of your data, by default it executed shallow copies, known as move.
    


    
Therefore, any automatic copying can be assumed to be inexpensive in terms of runtime performance.

    


    

    

      let outer_planet;
  let other_planet;
  let outer_value: i32;
  {
    let inner_planet= String::from("Mercury");
    let inner_value = 54;
    println!("inner_planet: {inner_planet}");
    println!("inner_value: {inner_value}");
    outer_planet= inner_planet;
    outer_value= inner_value;
    other_planet = outer_planet.clone();
    println!("outer_value: {outer_value}");
    println!("other_planet:{other_planet}");
  }

    

    


    
In case a variable content lives on the heap, the mechanism of ownership applies.
    
If a variable lives on the stack and it has a known size (e.g. built-in types), the datum is always copied 
    
(it implements the copy trait), there is no transfer of ownership, so the ownership mechanism does not apply.
    

    
  Built in data types are always deep copied.
    
  Built-in types implement the Copy trait, they are stored in the stack and theyt are trivially copied..
    
  Tuples implement it, if the constituent parts implement the Copy trait.
    
  If a type implements the Copy trait, variables that use it do not move, but rather are trivially copied, making them still valid after assignment to another variable.
    
  Rust won’t let us annotate a type with Copy if the type, or any of its parts, has implemented the Drop trait. 
    
  Nothing that requires allocation can implement Copy. 
    

  
      
    
    •  the copy is done for stack-only data types, such as integer and floating point
      • 
    
    •  copying is done implicitly, cloning must be done explicitly using the clone() method.
      • 
    
    •  Rust has a special annotation called the Copy trait that we can place on types that are stored on the stack.
      
        If a type implements the Copy trait, the copy is trivial, the move is not used.
      
        Rust won’t let us annotate a type with Copy if the type, or any of its parts, has implemented the Drop trait.
      
      
      • 
  
    
  So, it is important to know if a certain value lives on the heap or on the stack.

    . Lifetime
    
The concepts of scope and lifetime are related.
    


    .. Lifetime: Lifetime Annotation
    
Examples of lifetime annotations

    

      &i32        // a reference
  &'a i32     // a reference with an explicit lifetime
  &'a mut i32 // a mutable reference with an explicit lifetime

    

    

The syntax to explicitly define a generic lifetime for parameters.
    
Note that the lifetime annotations are all in the function signature, not the body.
    
So, lifetime annotations are part of the function contract, not the implementation.
    

    

      fn best_fuel <'a >(x: &'a str, y: &'a str) -> &'a str {
    [...]
  }

    

    
The above lifetime annotation states that the returned reference is valid as long as both parameter references are valid.
    

We state that x and y have the same lifetime. The compiler uses the most restrictive of the two.
    
Such lifetime is assigned also to the result.
The compiler thus checks the variable that gets assigned the result against the expected lifetime.

    
Remember, when we specify the lifetime parameters in this function signature,
we’re not changing the lifetimes of any values passed in or returned. 
    
Rather, we’re specifying that the borrow checker should reject any values that do not adhere to these constraints.

    

When returning a reference from a function, the lifetime parameter for the return type needs to match the lifetime parameter for one of the parameters.
    
If the reference returned does not refer to one of the parameters, it must refer to a value created within this function.
    
However, this would be a dangling reference because the value will go out of scope at the end of the function.


    ... Lifetime: the lifetime syntax
    
In the method argument, there is a backtick after the ampersand, before the data type.
    


    

      fn best_fuel <'a >(x: &'a str, y: &str) -> &'a str { // Not all parameters must be annotated.
    [...]
  }

  fn best_fuel <'a,'b>(x: &'a str, y: &'b str) -> &'a str { // Multiple lifetime annotations.
    [...]
  }

    

    
It is better to annotate all parameters, to be more explicit.
    
The second version of best_fuel() is better.

    


    ... Lifetime: the static lifetime
    

      
  
    • The static lifetime annotation indicates references that are available for the entire duration of the program.
      
      For example: string literals. It must be annotated explicitly.
      • 
  
    • Static lifetime can be coerced to a more strict lifetime, if the referenced is passed as output parameter from a function with another lifetime annotation, although it is rarely done.
      • 
  
    • 'static can be used as a trait bound, to ensure that the data will only contain static elements.
      
    Example:
      
    T: Display + 'static
   
      • 

    


    

    

    


    


    .. Lifetime: Lifetime elision rules.
    
There are situations when the borrow checker can infer the lifetime on its own,
so adding the lifetime annotation is not necessary.

    

      
  
    •  A set  of rules for the compiler to analyze reference lifetimes. 
      • 
  
    •  It describes situations that do not require explicit lifetime annotations. 
      • 
  
    •  If the code matches those situations, explicit lifetime annotation is not needed. 
      • 
  
    •  If there is any ambiguity, explicit annotation is still required. 
      • 

    

    


    .. Lifetime: the elision rules.
    
Lifetime elision in the Rust book. 
    

      
  
    • Rule 1: each input parameter that is a reference is assigned its own separate lifetime: 
      so if the function returns a reference, the compiler does not know what to do and it returns an error
      • 
  
    • Rule 2: of there is only one input lifetime, it is assigned to all output lifetimes
      • 
  
    • Rule 3: if there is a &self or &mut self input parameter,
              its lifetime is assigned to all output parameters
      • 

    
In the future, additional rules can be added.
    
If the rules do not hold, the compiler requires the explicit lifetime annotation.

In Rust functions cannot access variables outside their scope, unless they are consts or static variables (184).
    
A closure can capture its scope (189).

  let add_one_v2 = |x: u32| -> u32 { x + 1 };

      •

    . Smart Pointers
    
Smart pointers implement the Deref and Drop traits.
    
The Deref trait allows an instance of the smart pointer struct to behave like a reference so you can
write your code to work with either references or smart pointers. 
    
The Drop trait allows you to customize the code that’s run when an instance of the smart pointer goes out of scope.


    .. Deref coercion
    
Deref coercion converts a reference to a type that implements the Deref trait into a reference to another type.
    
For example, deref coercion can convert &String to &str because String implements the Deref trait such that it
returns &str.
    
When the Deref trait is defined for the types involved, Rust will analyze the types and use Deref::deref as many times as necessary to get a reference to match the parameter’s type. The number of times that Deref::deref needs to be inserted is resolved at compile time, so there is no runtime penalty for taking advantage of deref coercion!

    .. Patterns: Creational: Default pattern
    
Default pattern: implement the Default trait in your data types.
    
MyType::new() calls the default constructor.
    

    

    impl Example {
    T::new() -> Self {
        Self::default()
    }
}

    

    

Use the default to specify a default enumerator.
    

    

    #[derive(Default)]
enum Size {
    Small,
    #[default]
    Medium,
    Large,
}

    

    

Having a default is not appropriate when a field must have a non default, chosen value.
    


    .. Patterns: Creational: Builder pattern
    
When a type has a constructor that would require default or named parameters.
    
Create a builder to keep track of the constructor parameters. All Builder field are Optional.
    
Each Builder method modifies an Optional field and returns a reference to itself.
