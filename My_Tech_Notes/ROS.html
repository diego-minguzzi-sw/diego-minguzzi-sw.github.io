... ROS1 book: the Parameter server

A parameter server is a shared, multi-variate dictionary that is accessible via network APIs.
Nodes use this server to store and retrieve parameters at runtime.
As it is not designed for high-performance, it is best used for static, non-binary data such as configuration parameters.

The Parameter Server is implemented using XMLRPC and runs inside of the ROS Master, which means that its API is accessible via normal XMLRPC libraries. Wiki on the Parameter server
The parameter server is used for:

  • Controller gains
  • Coordinate transform parameters
  • Sensor intrinsing and extrinsic calibration parameters
  • Robot models
Remove all constants from the code and store them as parameters loaded when the node starts.
Nodes typically read parameters upon start-up, then they are unaware of changes to the parameters. 
  rosparam set /gains "p: 1.0
  i: 2.0
  d: 3.0"
Then: 
  rosparam list
  /gains/d
  /gains/i
  /gains/p
Parameters can change data type during the session (!).
The entire robot description is loaded as a parameter file, to a given parameter item.
The model is then available both for control algorithms and visualization displays. (88).

. Concepts Overview

The ROS2 graph is composed of: nodes, services, actions, topics.
Artifacts are distributed as packages, packages compose stacks. e.g. the navigation stack.
A node is an active entity, responsible for a single purpose.
An executable can contain one or more nodes.
A node can send and receive data via topics, services, actions, parameters.

A node may publish data to any number of topics and simultaneously have subscriptions to any number of topics.
Topics are a publish-subscribe mechanism. Topics are one of the main ways in which data is moved between nodes and therefore between different parts of the system.

Services are a request-response mechanism.

([NW18]) The Pub/Sub mechanism is flexible, but the publisher does not know if its messages are received.
Moreover, the subscribes does not know who is the publisher.
Using a req/reply service, the client and the server must be running at the same time. Most nodes have the same structure for managing parameters: 

  /teleop_turtle/describe_parameters
  /teleop_turtle/get_parameter_types
  /teleop_turtle/get_parameters
  /teleop_turtle/list_parameters
  /teleop_turtle/set_parameters
  /teleop_turtle/set_parameters_atomically

The format of the service call is : 

ros2 service call <service_name> <service_type> <arguments>
 The <arguments> part is optional. For example, services that have Empty type as arguments don’t have any arguments.

Parameters A parameter is a configuration value of a node.
You can think of parameters as node settings.
A node can store parameters as integers, floats, booleans, strings, and lists.
In ROS 2, each node maintains its own parameters.

  ros2 param list --param-type # Lists all parameters 
  
  ros2 param dump /turtlesim > turtle_params.yaml # Dumps params to a file (saves them).
  ros2 param load /turtlesim turtle_params.yaml # Loads all parameters to a node.  
  ros2 run turtlesim turtlesim_node --ros-args --params-file turtle_params.yaml # Loads the params when it runs an exec.

Actions
Actions are one of the communication types in ROS 2 and are intended for long running tasks.
Actions are like services that allow you to execute long running tasks, provide regular feedback, and are cancelable.
Actions:

  • accept a goal
  • provide a feedback stream
  • provide a result
The Action client requests a goal to the server.
The Action server acknowledges the goal, starts sending a feedback stream and eventually a result.

In the tutorial, the /turtle1/rotate_absolute action has /teleop_turtle as client and /turtlesim as server.
Note that a node declares to be a client to a given action.
Given an action, for example /turtle1/rotate_absolute, in order to inspect the action data type: 

  minguzzi@mingux:~$ ros2 action list -t
  /turtle1/rotate_absolute [turtlesim/action/RotateAbsolute]
  
  minguzzi@mingux:~$ ros2 action info  -t /turtle1/rotate_absolute
  Action: /turtle1/rotate_absolute
  Action clients: 1
      /teleop_turtle [turtlesim/action/RotateAbsolute]
  Action servers: 1
      /turtlesim [turtlesim/action/RotateAbsolute]
      
  minguzzi@mingux:~$ ros2 interface show turtlesim/action/RotateAbsolute
  # The desired heading in radians
  float32 theta
  ---
  # The angular displacement in radians to the starting position
  float32 delta
  ---
  # The remaining rotation in radians
  float32 remaining

When we show the interface:

  • the first section describes the goal
  • the second section describes the result
  • the third describes the feedback

Explanation of log levels:

  • Fatal messages indicate the system is going to terminate to try to protect itself from detriment.
  • Error messages indicate significant issues that won’t necessarily damage the system, but are preventing it from functioning properly.
  • Warn messages indicate unexpected activity or non-ideal results that might represent a deeper issue, but don’t harm functionality outright.
  • Info messages indicate event and status updates that serve as a visual verification that the system is running as expected.
  • Debug messages detail the entire step-by-step process of the system execution.
