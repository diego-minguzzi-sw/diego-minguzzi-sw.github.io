.. ROS2 Scratch: Communication mechanisms

... ROS2 Scratch: Nodes

A node runs on top of a computer program, it uses ROS2 functionalities, like: logging, communication with other nodes, etc. ROS has mechanisms to handle communication between nodes.
Rename a node at runtime:
ros2 run my_cpp_pkg my_first_node --ros-args -r __node:=abcd

... ROS2 Scratch: topics

Topics are useful to stream data and commands from a node into another.
  • A node publishes to the topic, another node subscribes to the topic.
  • a topic is defined by a name and a data type.
    Publishers and subcribers use the same name to make communication successful.
    The data type of the topic is called interface
  • The kind of message sent through an topic is called interface
Message definitions are defined in the msg subbirectory in the package.

... ROS2 Scratch: Bag files

    # Example of how to record the topic number
    ros2 bag record --compression-mode file --topics /number
    ros2 bag record --compression-mode file --topics /number -o number_topic
    
    # Play back a recorded bag.  Start paused.
    ros2 bag play -p rosbag2_2025_12_26-09_22_50
ROS2 commands:
  • ros2 topic info [topic_name]
  • ros2 interface show [interface data type]

... ROS2 Scratch: services

Services provide a client server mechanism·
Services are defined by a name, the interface is composed by the request data type and the response data type.
So a service is defined by a name and an interface (request, response).
A service is provided by a server.
A service can have multiple clients. Clients are not aware of each other.
Clients reach the server only by the service name. They do not know the service IP address.
Service interfaces are defined in the srv subbirectory in the package. 

    # Example: how to call a service from the command line.
    ros2 service call /reset_counter  my_interfaces/srv/ResetCounter "{ reset_value: 0 }"

... ROS2 Scratch: when using topics? when services?

  • Topics: a continuous stream of data when the most recent datum instance is the most important
  • Services: actions on demand, requested from time to time, not periodically.

... ROS2 Scratch: actions

An action has a name and an interface. The interface is composed of:
  • goal: similar to the service request
  • result: similar to the service response
  • feedback: additional data during the action execution
Actions are used when you need a client/server communication and the action takes time to execute.
An action is identified by a name and an interface. There is only one action server for each action name-interface.
Action Client Action Server
The client requests a Goal (service request) The server either accepts or rejects the Goal.
... ...
The client can later cancel the Goal (service request) The server returns a response code.
... ...
The server can return feedback (topic)
... ...
  The server can return Goal status (topic)
... ...
The client can request the Result of the action execution (service request). The server returns the Result.
Example of calling an action from the terminal: 
    ros2 action send_goal /MyTurtle/rotate_absolute turtlesim/action/RotateAbsolute "{theta: 1.57}"

... ROS2 Scratch: parameters

Parameters are runtime settings to a node. Parameters exists within a node
It is possible to set parameters on the fly during a node execution.
Syntax to override/set parameters from the command line. Otherwise, it is possible to set parameters when a node is run.
    ros2 run turtlesim turtlesim_node --ros-args -p background_r:=0 -p background_g:=120 -p background_b:=0
    
    # Syntax to override parameters from the command line.
    ros2 run my_py_pkg my_publisher --ros-args -p number:=10  -p publish_period:=0.5

.... ROS2 Scratch: parameter files

Dumping parameters to a file, loading them at launch time. 
    # Dump parameters to a file
    ros2 param dump /my_publisher > params/my_publisher_params.yaml
    
    # Then, parameters can be installed by adding the lines below to the CMakeLists.txt
    install( DIRECTORY params/ DESTINATION share/${PROJECT_NAME}/params )
    
    # Then refer to the installed parameters when running a node:
    ros2 run my_cpp_pkg my_publisher \
             --ros-args \
             --params-file $(ros2 pkg prefix my_cpp_pkg)/share/my_cpp_pkg/params/my_publisher_params.yaml
$(ros2 pkg prefix my_cpp_pkg)

A ROS2 distribution is made-up of packages.
The base environment is called underlay.

A running ROS2 application forms a computation graph.
A CG is made of nodes that communicate with each other, using the provided architectural mechanisms:
  • Publish / subscribe: N nodes publish to M subscribers using a channel called topic, accepting messages of a given type
  • Services
  • Actions: an action is an asynchronous communication
A function of a node is processing or control. Control needs iterative execution, processing requires event-oriented execution.
(7) The standard message to control the robot speed is geometry_msgs/msg/Twist

If a resource name begins with a tilde, it is private, if it begins with / then it is absolute.

  ros2 interface show sensor_msgs/msg/Image # Standard type for images
ROS2 is organized into packages; packages reside in the workspace. A workspace has a src directory in it.
A workspace must be activated. There can be many workspaces active at the same time (11).

The first activeted workspace is called underlay.
Suppose an underlay workspace is activated, then another package can overlay the previous.
The entire ROS2 distribution is the underlay workspace.

. ROS2 Architecture

Top to bottom: rclcpp, rclpy, etc. are ROS Client API packages, each for a given programming language. All of them sit on RCL.
rcl: ROS Client Library: the language specific APIs sit on top the the RCL: rclcpp, rclpy, etc.
rmw: ROS Middleware Layer: the communication layer, in turn it uses a DDS version. RMW adapts the underlying DDS version to the RCL.

.. ROS2 Arch: logging

All nodes send their logging to the topic /rosout; the data type is rcl_interfaces/msg/Log.
Setting the log level 
  # Runs a node and sets the log level.
  ros2 run first_pkg hello_node --ros-args --log-level info

.. ROS2 Arch: pubsub

  • Multiple publishers can publish to the same topic. The QOS queue is on the publisher.
  • Multiple subscribers can subscribe to the same topic
  • The topic communication mechanism is many-to-many

... ROS2 Arch: pubsub. QoS

  • About-Quality-of-Service-Settings
QoS policies form a QoS profile:
The Subscriber must have a policy less or as restrictive then the publisher.
  • History: Keep last N / Keep All
  • Depth: honored if History is Keep last
  • Reliability: Best effort / Reliable may try multiple times
  • Durability: Transient local= late joining subscribers receive the last sample / Volatile= samples are not persisted
  • Deadline: duration: the expected maximum amount of time between subsequent messages being published to a topic
  • Lifespan: the max time between publish and message receive. If exceeded, the message is considered stale
  • Liveliness: whether a topic is still considered alive (Automatic / Manual)
  • Lease Duration: the maximum period of time a publisher has to indicate that it is alive before the system considers it to have lost liveliness (losing liveliness could be an indication of a failure).

.. ROS2 Arch: interfaces

In ROS2, messages, services and actions are interfaces.

.. ROS2 Arch: messages

ROS2 messages are defined in packages that by default end with _msgs Messages are composed of fields. Stamped messages have an header field. 
  ros2 interface show geometry_msgs/msg/Point
  ros2 interface show geometry_msgs/msg/PointStamped # Contains header and Point

  ros2 interface proto std_msgs/msg/String      # Provides an example of a message of a given type.
Suppose that a message is called std_msgs/msg/Int32 :
  • The header is std_msgs/msg/int32.hpp
  • The data type is std_msgs::msg::Int32
