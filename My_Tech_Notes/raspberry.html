#include 

int main()

  int a{5};

makefile file: 
hello_rpy: hello_rpy.cpp makefile
	${CXX} -o hello_rpy -g hello_rpy.cpp

Notes

  • the ssh-server-openssh must be added to the IMAGE_FEATURES, in place of the ssh-server-dropbear.
  • By default, the toolchain creates dynamically linked binaries. To create statically linked binaries, add:
    IMAGE_INSTALL_append = " glibc-staticdev"

bitbake image -c populate_sdk

 The issue was solved by adding the linux-firmware to the IMAGE_INSTALL variable.
The solutions listed here do not work.

The static configuration in the interfaces file works if the linux-firmware is added to the image
My current /etc/network/interfaces file is: 

# /etc/network/interfaces -- configuration file for ifup(8), ifdown(8)
 
# Wired or wireless interfaces
auto eth0
iface eth0 inet static
address 192.168.10.5
netmask 255.255.255.0

# The loopback interface
auto lo
iface lo inet loopback
		
# Bluetooth networking
iface bnep0 inet dhcp

NOTE: do not add the gateway line to the eth0 configuration, otherwise the Raspberry will not be able to resolve names using the DNS, that is accessed by means of the wifi network.

How to add support for WiFi

In the local.conf , add the line:

IMAGE_INSTALL_append = " linux-firmware wpa-supplicant"
wpa_supplicant file:
ctrl_interface=/var/run/wpa_supplicant
ctrl_interface_group=0
update_config=1

network={
    key_mgmt=WPA-PSK
    ssid="BBBELL-D3AD"
    psk="CsGeviP1995_BrqPX8"
}
The solution described here adds way too many image features and layers, beside that, it is for a previous version of Yocto.

How to remove the splash screen at boot

In the local.conf, add the line: 
IMAGE_FEATURES_remove = "splash"

How to add a full command line

In the local.conf, add the line: 
IMAGE_INSTALL_append = " packagegroup-core-full-cmdline"

6. Notes on the Yocto project

Based on the OpenEmbedded (OE) project, which uses the BitBake tool to construct Linux images.
Source Directory = locally installed Yocto Project files.
The supported BSP(s) are maintained in their own layers.
Poky build tool:
  • BitBake
  • OpenEmbedded core = (meta)
  • Yocto-specific metadata meta-yocto
  • Yocto specific BSP The naming scheme is meta-bsp_name, es.meta-raspberrypi
The build process creates the Linux distribution and the toolchain from source. In order to flash, see Flashing Images Using bmaptool

Building the image

  • BitBake searches build/conf/bblayers.conf, reads the BBLAYERS, for each directory in the list:
    • A build/conf/layer.conf is searched. (BBPATH is automatically set)

Terms

  • Build environment: it is created by sourcing oe-init-build-env
  • Classes: a simple inheritance mechanism allowing recipes to share common workflows (.bbclass extension)
  • Configuration files, .conf extension, define the global content. They can set or overwrite variables, those settings are global.
    • bblayers.conf : contained in the build environment directory
    • bitbake.conf is the main configuration file. BitBake expects that a bitbake.conf is present in every directory listed as metadata.
    • layer.conf : exists in every layer metadata directory. Contains the variables and paths to find the recipes
    • local.con build environment configuration
    • Machine configuration files
  • Append files .bbappend append recipe information to a recipe file .bb file, located in the same directory. BitBake verbatim appends the contents of an append file to the corresponding recipe.
    Append files are commonly used by layers building on top of other layers.
  • BSP: documents, source and binaries to enable an operating system to run on a target hardware platform.
  • Image: the binary output that runs on a specific hardware or QEMU: it can be copied to a storage medium, and then the target can boot and run.
  • Layer = a collection of recipes
    • Recipe : a set of instructions implementing the build flow for a particular package.
      A recipe can set a variable, but that setting is local to the recipe.
      A logical unit of tasks to be executed: normally it is a package to be built. A recipe declares the artifacts it depends on, by the DEPENDS variable. The tasks are determined by the Open Embedded workflow. BitBake itself does no impose any workflow.
      • Fetch: do_fetch fetches the source and makes it available in the WORKDIR directory
      • Extract: do_unpack
      • Patch: do_patch
      • Configure: do_configure
      • Build: do_compile
      • Install: do_install
      • Package: packaging is needed in order to bunding files into a single archive for distribution and installation into the target system
  • Metadata: any file (classes, recipes, configuration files, etc) instructing Bit
  • Package: either
    • the OS specific file to distribute a sw component
    • in yocto: the recipes and other metadata to build the respective software bundle
  • Recipe file .bb; a recipe is a metadata containing the directives to build a sofware package.
    Note on recipe names:
    There seem to be certain rules regarding .bb files naming, but apparently those are not written anywhere. Some of those rules seem to be ( see here):
    • No spaces
    • Underscores can only by used to separate name and version
    • No ASCII special characters
    • No non-ASCII characters
    • No uppercase letters
Classes and recipes describe the tasks to be run. A recipe can inherit one or more classes. Metadata is divided into three groups: configuration, class and recipe.

Generating the root filesystem image

The rootfs can be seen as a ready to use filesystem for a target.
  • Generate the rootfs directory tree
  • Populate the rootfs
  • wraps the final filesystem
  • compress, if necessary
The rootfs image generation is performed by the subtasks of do_rootfs. The list of packages is the union of IMAGE_INSTALL and IMAGE_FEATURES, filtered by PACKAGE_EXCLUDE.
The generated image is placed in build_dir/tmp/deploy/image//machine

The build directory

The build directory contains:
  • conf: it contains local.conf, etc
  • downloads, the downloaded packages, unless it was configured to be somewhere else
  • sstate-cache it contains packaged data snapshots. It is a cache used to speed the build process.
  • tmp the temporary build directory. The most important directories are:
    • deploy<: the build products /li>
    • sysroots the shared libraries, headers, utilities that are used in the process of building recipes
    • work
As mentioned, the tasks are:
  • do_fetch downloads the packages in the download directory
  • do_unpack unpacks the downloaded packages in the build/tmp/work directory
  • do_patch in the build/tmp/work directory
  • do_configure
  • do_compile
  • do_install the built artifacts are installed in the proper directory under build/tmp/work/...
  • The packages are shared and possibly modified under build/tmp/sysroot

Variables in local.conf:

  • BBLAYERS in bblayers.conf : the paths to allo the the layers included by the build environment
  • BBFILES in bblayers.conf : the recipe file list
  • IMAGE_INSTALL : the list of packages to be included in the image
  • TOPDIR : the full absolute path to the build directory
  • TMP_DIR : it is specific to the build, the temporary directory can be under the build directory

7. Embedded Linux

In embedded systems, the bootloader has the same functionality as the BIOS in a desktop PC [31].
When the board is started, the bootloader performs the low-level hardware initialization, and it prints some messages to the console or to the serial line.
Then, the bootloader loads and boots the kernel.
Then, the bootloader transfers the control to the kernel and (the bootloader) ceases to exist.
[36] Linux requires a filesystem: a predefined set of directories and files with a specific layout.

When the kernel initialization is terminated and the filesystem is mounted, the kernel spawns the init program.[37]
Before the init execution, the kernel was running, in kernel mode, where it is able to access all of the memory.
The init runs in user space.

Memory Space

Legacy embedded systems had one address space where all memory was mapped: DRAM, peripherals, Flash, etc.
Linux configures the Memory Management Unit (MMU)

8. Notes on OpenGL ES

  • Vertex shader: a general purpose programmable method for operating on vertices.
    The shader program operates on the vertices. It is written using the shading language
    Vertex shader inputs: the position of the vertices.
  • The output f the vertex shared is passed to the primitive assembly.
    Primitives are assembled from vertices.
  • Rasterization converts primitives into two-dimensional fragments.
    2D fragments are pizels with attributes like color, that can be drawn on the screen.
    The output of the rasterization process are 2D fragments.
  • Fragment shader: a general purpose programmable method for operating on fragments.
  • Per-Fragment operations
Open GL ES require a rendering context and a drawing surface.
  • The rendering context stores the appropriate OpenGL ES state.
  • The standard does not specify how the rendering context is attached to the windowing system.
  • EGL is the interface between the rendering context and the native window system.
Any Open GL application must perform the following tasks
  • Initialize the display.
  • Create a rendering surface, either on-screen surface or off-screen surface
  • Create a rendering context.
Typical steps in an OpenGL ES program:
  • Load and compile the shaders: the vertex and fragment shaders.
  • Create the program object: all shaders are attached to the program, then the program is linked.
Raspberry Pi has OpenGL 2.1 and OpenGL ES 2.0.
